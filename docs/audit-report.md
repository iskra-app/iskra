## CRITICAL

### C1. Обновлённый токен никогда не сохраняется — сессия не переживёт ротацию refresh-токена ✓ проверено
- **Файл:** `Sources/IskraCore/Session/AuthenticationService.swift` — `persist()`, `makeClientBuilder()`
- **Уверенность:** high
- **Проблема.** `persist()` берёт `client.session()` ровно один раз, сразу после логина, и кладёт в
  Keychain. Больше `SessionStore.save` не вызывается **никогда**. При этом
  `disableAutomaticTokenRefresh()` не вызван, то есть автообновление токенов включено: SDK обновляет
  их сам и держит **только в памяти Rust-клиента**. В Keychain остаётся старая пара.
  Проверено грепом: `setSessionDelegate` не вызывается ни разу, при том что API в биндингах есть
  (`matrix_sdk_ffi.swift:3872`, `protocol ClientSessionDelegate` — `:43395`).
- **Сценарий.** MAS/OAuth **ротирует** refresh-токен — старый становится невалиден в момент
  использования. Пользователь входит, работает сутки, SDK молча обновляет токен, пользователь
  убивает приложение. Холодный старт → `restoreSession` со **старой** парой → `M_UNKNOWN_TOKEN` →
  `IskraRootView.restore()` глотает ошибку и показывает экран входа. Человек «сам вышел» без
  объяснений, а на диске остаётся зашифрованный store с ключами комнат, который уже никто не удалит
  (см. M9).
- **Как чинить.** `SessionStore` (или тонкая обёртка) реализует `ClientSessionDelegate`:
  `retrieveSessionFromKeychain(userId:)` → `loadSession()?.rustSession`,
  `saveSessionInKeychain(session:)` перезаписывает `StoredSession`, **сохраняя `sessionID`** (иначе
  теряются пути к директориям). Потокобезопасно и **не** `@MainActor`: SDK зовёт с Rust-потоков.
  `.setSessionDelegate()` в `makeClientBuilder` — до `build()`, на обоих путях (вход и restore), и в
  `PushDecoder` тоже, иначе refresh в расширении разойдётся с приложением.

### C2. Отмена во время `.finishing` не отменяет — видеосообщение всё равно уходит в комнату ✓ проверено
- **Файл:** `Sources/IskraFeatures/VideoNote/VideoNoteRecorder.swift` — `stop()`, `cancel()`
- **Уверенность:** high
- **Проблема.** `stop()` копирует обработчик в локальную переменную до асинхронной работы:
  `let handler = onRecorded; onRecorded = nil; Task { … await handler(square) }`. `cancel()` умеет
  обнулить только поле — на уже запущенный `Task` он не влияет, а `take` к этому моменту забран
  `close()`. Счётчика поколений, как `generation` в `VoiceRecorder`, здесь нет.
- **Сценарий.** Записал кружок → отпустил (идёт экспорт квадрата, секунды на длинном клипе) →
  нажал «Отмена» (кнопка нарисована всегда) → оверлей закрылся, человек уверен, что записи нет →
  через секунду в комнате появляется кружок с его лицом. Ровно тот класс дефекта, который
  `VideoNoteWriter` в шапке файла называет худшим, что делало это приложение.
- **Как чинить.** Счётчик поколений, как в `VoiceRecorder`: инкремент в `cancel()` и `stop()`,
  проверка перед `await handler(square)`; иначе — только удалить файлы. Плюс прятать «Отмену» в
  состоянии `.finishing` (или вести её к тому же поколению).

### C3. `VideoNoteRecorder.prepare()` без защиты от отмены — камера и микрофон остаются включёнными ✓ проверено
- **Файл:** `Sources/IskraFeatures/VideoNote/VideoNoteRecorder.swift` — `prepare()`
- **Уверенность:** high
- **Проблема.** `prepare()` проходит **три `await`** (два разрешения + сборка сессии на detached-таске
  с `startRunning()`), и ни после одного из них не проверяется, что запись отменили. `cancel()` →
  `teardown()` выставляет `session = nil, state = .idle`, а докатившийся `prepare()` **перезаписывает
  это работающей сессией**.
- **Сценарий.** Зажал кнопку → оверлей поднялся, идёт сборка сессии (0.3–1 с, в первый раз — алерт
  разрешений) → отпустил/свайпнул влево/ушёл с экрана → `cancel()`, оверлей исчез → `prepare()`
  возвращается и поднимает `AVCaptureSession` с камерой и микрофоном. UI пуст, индикатор камеры
  горит, сессия живёт, пока открыта комната. Второй вариант: после `cancel()` (`state == .idle`)
  повторное удержание проходит `guard` и запускает **вторую** `prepare()` параллельно первой.
- **Как чинить.** Тот же `generation`: снимок в начале, проверка после каждого `await`; если
  поколение сменилось — `built.session.stopRunning()` и выход.

## HIGH

### H1. Интерактивной верификации устройств нет, и доверие нигде не проверяется ✓ проверено
- **Файл:** `Sources/IskraCore/Session/Account.swift` (только читает `verificationState()`),
  `Sources/IskraFeatures/Settings/EncryptionView.swift`, `AuthenticationService.makeClientBuilder`
- **Уверенность:** high
- **Проблема.** Ни одного вызова верификационного API во всей базе. `makeClientBuilder` не задаёт ни
  `roomKeyRecipientStrategy`, ни `senderDeviceTrustRequirement` — действуют дефолты SDK (шифровать
  всем устройствам, показывать всё расшифрованное). Шилды (`getShields()`) не используются нигде.
  Списка чужих сессий нет в принципе (`DeviceListProbe` это честно доказал).
- **Сценарий.** В аккаунт собеседника добавляется устройство. Iskra молча шифрует Megolm-ключ и на
  него; входящее сообщение с непроверенного устройства визуально неотличимо от проверенного.
  Пользователь не может ни увидеть чужие сессии, ни отозвать их. Для E2EE-мессенджера это главный
  незакрытый риск.
- **Как чинить (по возрастанию цены).** (1) Шилды на входящих (`getShields()`) — дёшево и закрывает
  бóльшую часть слепоты. (2) `ClientBuilder.roomKeyRecipientStrategy(.errorOnVerifiedUserProblem)` —
  отправка ломается при смене identity доверенного пользователя. (3) SAS/emoji-верификация
  (`Encryption.requestVerification` → `SessionVerificationController`).

### H2. Приложение просит подтвердить устройство, а подтвердить его нечем — бесконечный retry ✓ проверено
- **Файл:** `Sources/IskraCore/Timeline/Message.swift` — `SendFailure.canRetry`;
  `Sources/IskraCore/Resources/ru.lproj/Localizable.strings:72`
- **Уверенность:** high
- **Проблема.** `canRetry == true` для `.insecureDevices`, `.identityChanged`, `.verificationRequired`.
  Строка: «Подтвердите это устройство… **Это делается в настройках**». В настройках верификации нет
  (H1). `retrySending` упирается в тот же wedge.
- **Сценарий.** Сообщение застревает навсегда, кнопка «Отправить ещё раз» — бесконечный цикл. Хуже:
  не сумев ничего сделать, человек нажмёт «Отменить» и напишет заново — то есть **обойдёт** защиту,
  которая как раз сработала правильно.
- **Как чинить.** Пока нет верификации — честный текст, не обещающий кнопки, которой нет
  (формулировки в `compliance-checklist.md`). Идеально — вместе с H1.

### H3. Пуши: нет запроса разрешения и нет регистрации в APNs — и это Swift, а не инфраструктура ✓ проверено
- **Файл:** нигде. Грепом: `setPusher`, `registerForRemoteNotifications`, `requestAuthorization` —
  **ноль совпадений** во всём `Sources/` и `Apps/`.
- **Уверенность:** high
- **Проблема.** `ROADMAP.md` этап 7 и `docs/PUSH-GATEWAY.md` подают остаток как «ни одна из них не
  пишется в Xcode». Это верно для Sygnal и **неверно** для клиента: запрос разрешения, регистрация в
  APNs, приём device token, badge и маршрутизация тапа по уведомлению — всё это пишется именно в
  Xcode, и всего этого нет. Без device token `setPusher` нечем вызвать даже когда шлюз появится.
- **Как чинить.** Дописать в ROADMAP честный список; реализовать
  `UNUserNotificationCenter.requestAuthorization` (после первого входа, не на старте — это уже
  правильно записано в PUSH-GATEWAY.md), `registerForRemoteNotifications`, приём токена и
  `Client.setPusher`.

### H4. Нет реакции на аннулированную сессию (`ClientDelegate.didReceiveAuthError`) ✓ проверено
- **Файл:** нигде — `client.setDelegate` не вызывается (API есть: `matrix_sdk_ffi.swift:3158`,
  `didReceiveAuthError(isSoftLogout:)` — `:43238`)
- **Уверенность:** high
- **Сценарий.** Пользователь завершает сессию Iskra с другого клиента, или админ деактивирует
  аккаунт. Iskra не узнаёт: sync начинает падать, список комнат замирает на кэше, отправка молча не
  уходит, приложение продолжает выглядеть рабочим. Ни одного сообщения на экране.
- **Как чинить.** Подписаться в `UserSession.start()`; на `didReceiveAuthError` — остановить
  `roomList`, почистить `SessionStore`, перевести `phase` в `.signedOut` с внятным текстом.

### H5. Бэкап ключей и cross-signing не включаются автоматически ✓ проверено
- **Файл:** `AuthenticationService.makeClientBuilder` (API есть: `autoEnableBackups` —
  `matrix_sdk_ffi.swift:3796`, `autoEnableCrossSigning` — `:3798`; дефолт обоих `false`)
- **Уверенность:** high
- **Сценарий.** Человек ставит Iskra, год переписывается, теряет телефон — история потеряна вместе с
  ключами, потому что бэкапа никогда не было. Он появляется, только если самому зайти в
  `EncryptionView` и нажать «защитить историю». Это ровно тот класс потерь, ради которого в
  `enableRecovery` уже стоит `waitForBackupsToUpload: true`.
- **Как чинить.** `.autoEnableBackups(true).autoEnableCrossSigning(true)` — одна строка. Ключ
  восстановления остаётся ручным, и это правильно.

### H6. Незавершённые Task переживают `stop()` и пишут состояние переоткрытого таймлайна
- **Файл:** `Sources/IskraCore/Timeline/TimelineStore.swift` — `stop()`, `page()`, `refill()`
- **Уверенность:** high (дефект), medium (частота)
- **Проблема.** Тело `refillTask` нигде не проверяет `Task.isCancelled` и досчитает до
  `isRefilling = false; rows = latestRows`. Задача внутри `page()` — неструктурированная, `stop()` её
  вообще не отменяет; она держит **старый** `timeline` и допишет `canLoadMore` уже после
  переоткрытия комнаты.
- **Сценарий.** Удалил сообщение (идёт `refill`) → ушёл с экрана (`stop()`) → вернулся (`start()`).
  Зомби-refill просыпается посреди `open()` и публикует пустой сброс свежего листенера — **комната
  мигает пустой**, защита `rebuildRows()` снята.
- **Как чинить.** `guard !Task.isCancelled` в теле `refillTask`; «поколение» открытия
  (`openGeneration`), инкремент в `stop()`, запись состояния только при совпадении; отменять задачу
  пагинации в `stop()`.

### H7. `TimelineStore.start()`: re-entrancy — два одновременных `open()` дают два листенера
- **Файл:** `Sources/IskraCore/Timeline/TimelineStore.swift` — `start()`, `open()`
- **Уверенность:** medium
- **Проблема.** Guard — `guard timeline == nil`, но `self.timeline` присваивается **после двух
  await**. Два вызова в этом окне пройдут guard оба: два `Timeline`, два `addListener`, две подписки
  на send queue и typing; оба листенера льют диффы в один `items` — дубли строк.
- **Как чинить.** Guard на *задаче*, а не на поле: `private var opening: Task<Void, Error>?`.

### H8. Крэш при `UInt64(abs(...))` — NaN/бесконечность не проверяются
- **Файл:** `Sources/IskraCore/Media/MediaMetadata.swift` (ориентированные размеры видео)
- **Уверенность:** medium
- **Проблема.** `UInt64(Double)` — trap, а не опционал. `naturalSize`/`preferredTransform` приходят из
  файла, который выбрал пользователь; повреждённый трек даёт NaN → **крэш процесса** вместо «файл не
  отправился». Рядом того же класса: `MediaLoader.thumbnail` (`UInt64(size)` при отрицательном),
  `SquareVideoExporter` (`CGFloat(side)/edge` при `edge == 0` → ∞ в трансформе).
- **Как чинить.** `UInt64(exactly:)` / проверка `isFinite && >= 0`; поля `width/height` уже
  опциональные, SDK это переживёт.

### H9. Нет реакции на `scenePhase` и на прерывание аудио
- **Файл:** весь `Sources/IskraFeatures/**` — `scenePhase`, `interruptionNotification`,
  `wasInterrupted` не встречаются ни разу
- **Уверенность:** high (отсутствие кода), medium (последствия)
- **Сценарий (голос).** Hands-free запись → входящий звонок → `AVAudioRecorder` остановлен системой →
  тикер видит `!recorder.isRecording` и просто `return`, **не меняя `state`**. Возвращаешься: полоска
  записи на месте, точка пульсирует. Жмёшь «отправить» → длительность считается **по стенным часам** →
  уходит голосовое, где в событии написано 3:40, а звука 12 секунд.
- **Сценарий (видео).** Locked-запись, свернул на минуту → кадр с `presentationTimeStamp` через 60+ с
  срабатывает как кэп → **клип уходит сам**, без действий пользователя.
- **Как чинить.** `@Environment(\.scenePhase)` в `RoomView`: на `.inactive/.background` — отмена
  записи; подписка на `AVAudioSession.interruptionNotification` в `VoiceRecorder`.

### H10. `AVAudioSession` активируется и никогда не деактивируется
- **Файл:** `Sources/IskraFeatures/Media/VoiceRecorder.swift`, `Support/PlaybackAudio.swift`
- **Уверенность:** high
- **Сценарий.** Играет подкаст → записал голосовое → отправил → категория осталась `.playAndRecord`,
  сессия активна. **Подкаст не возобновится, пока приложение не убито.** То же после отмены.
- **Как чинить.** `setActive(false, options: .notifyOthersOnDeactivation)` в `reset()`/`cancel()`.

### H11. Черновик незавершённой *правки* сохраняется как обычный — старое сообщение уходит вторично
- **Файл:** `Sources/IskraFeatures/Rooms/RoomView.swift` — `onDisappear`
- **Уверенность:** high
- **Проблема.** `startEditing` кладёт текст редактируемого сообщения в `draft`. `cancelContext()` его
  выбрасывает — и комментарий там прямо объясняет, почему это обязательно. Но `onDisappear` про
  `composerContext` не знает и сохраняет как обычный черновик.
- **Сценарий.** Правлю «Привет» → ухожу из комнаты → возвращаюсь → в композере «Привет», контекста
  правки нет → жму отправить → в комнате **второе** «Привет» новым сообщением.
- **Как чинить.** В `onDisappear` не сохранять черновик, если `composerContext == .editing` (или
  сохранять тип черновика — SDK умеет `ComposerDraftType.edit(eventId:)`).

### H12. VoiceOver: приложением нельзя пользоваться — только читать
Две находки, одна причина:
- **H12a. Кнопка записи не является кнопкой.** `MessageComposer` — это `Color.clear` с
  `DragGesture`. Есть `accessibilityLabel` и `.isButton`, но **нет `accessibilityAction`**. VoiceOver
  не синтезирует drag: двойной тап не делает ничего. Записать голосовое невозможно.
- **H12b. `.accessibilityElement(children: .combine)` на строке сообщения хоронит все кнопки внутри
  пузыря** (`MessageRow`): play/pause голосового, тап по кружку, открытие фото, открытие файла,
  «Отправить заново». Ни одного `accessibilityAction` на строке не добавлено.
- **Уверенность:** high
- **Как чинить.** `.accessibilityAction` на кнопке записи (начать / закончить и отправить / отменить);
  `.accessibilityAction(named:)` на строке сообщения для каждого действия, которое было в дочерних
  кнопках. Строки для них уже существуют. `.combine` оставить — одна строка = одна мысль, это верно.

## MEDIUM

### M1. Ключ восстановления уходит в общесистемный буфер обмена ✓ проверено
`Support/Clipboard.swift` — `UIPasteboard.general.string = text`, без `.localOnly` и без
`.expirationDate`. Ключ — пароль ко **всей** истории аккаунта — синхронизируется через Universal
Clipboard на другие устройства, читается любым приложением и лежит бессрочно. `Account.swift`
справедливо пишет, что ключ «никогда никуда не записывается» — а через `Clipboard.copy` он
записывается в самое публичное место в системе. **Чинить:** отдельный путь для секретов —
`setItems(_:options:)` с `.localOnly` и минутным `.expirationDate`; на macOS — `.concealed`-тип.

### M2. Probe-код печатает расшифрованное тело и вкомпилирован в релиз ✓ проверено
`Apps/Shared/NotificationProbe.swift` печатает `title`/`sender`/`body` — расшифрованное сообщение —
через `print`, а гейт только `CommandLine.arguments`, без `#if DEBUG`. У GUI-приложения stdout уходит
в unified log, где `print` не редактируется. `DeviceProbe` печатает ответ `/devices`. **Чинить:**
обернуть все четыре probe в `#if DEBUG`; в `NotificationProbe` печатать факт расшифровки и длину.

### M3. Логи ошибок: половина утечёт, половина бесполезна
Два стиля в базе. 14 сайтов пишут `\(String(describing: error), privacy: .public)` — а `NSError` от
Foundation/Photos/QuickLook почти всегда несёт `NSFilePath` в `userInfo`, то есть в системный лог
может уйти **имя файла пользователя** (`паспорт_скан.pdf`). Другие 20 сайтов пишут голое `\(error)` —
и `os.Logger` по умолчанию отредактирует это в `<private>`, то есть лог, заведённый ровно потому, что
«на телефоне нет отладчика», на телефоне ничего и не покажет. **Чинить одним решением:** логировать
`(error as NSError).domain` + `.code` с `privacy: .public` — это и есть «какой из шагов упал», ради
чего лог заводили, и там нет ни имён файлов, ни тел ответов.

### M4. macOS: расшифрованный файл остаётся в /tmp навсегда ✓ проверено
`Media/FileOpener.swift` — `handOff` копирует плейнтекст в `temporaryDirectory` **под именем
отправителя** и не удаляет никогда: ни при закрытии, ни при выходе из аккаунта. Открыл десять PDF —
осталось десять. **Чинить:** своя поддиректория (`…/T/iskra-handoff/<uuid>/`), уборка при следующем
открытии, при `signOut` и при завершении приложения.

### M5. `signOut()` не гасит живые сторы — листенеры работают по удалённому store
`UserSession.signOut()` останавливает `roomList`, но не выданные `TimelineStore`/`PinnedStore`.
`PinnedStore.stop()` **вообще никто не зовёт** (грепом). На Mac/iPad комната остаётся открытой в
detail-колонке, то есть в момент `logout()` (который удаляет SQLite с диска) живы `addListener`,
`subscribeToRoomInfoUpdates`, `subscribeToSendQueueUpdates`, `subscribeToTypingNotifications`.
**Чинить:** реестр выданных сторов в `UserSession` (`[weak …]`), `stop()` до `logout()`. Это же
закрывает M6 и L-находку про `onDisappear`.

### M6. `PinnedStore.stop()` — мина: стор, который нельзя запустить заново
`stop()` снимает листенер, но не обнуляет `timeline`, а `start()` начинается с
`guard timeline == nil else { return }` → стор мёртв навсегда. Это ровно тот дефект, который в
`TimelineStore.stop()` подробно описан как исправленный. Сейчас спасает только то, что `stop()`
никто не вызывает (см. M5) — то есть мина ждёт первого, кто честно погасит стор.

### M7. Кросс-процессная ротация токена без лока
`.multipleProcesses` в `notificationClient` разводит по локу крипто-store, но не refresh-токен. В
FFI есть `ClientBuilder.crossProcessLockConfig` (`:3810`) — не вызывается. Push приходит, пока
приложение живо, у обоих процессов истёк access token, оба идут за refresh — второй получает уже
отозванный. Выглядит как «приложение само разлогинилось ночью». **Чинить** вместе с C1.

### M8. Sync не останавливается в фоне и не перезапускается после ошибки
Стартует в `UserSession.start()`, останавливается только в `signOut()`. Подписки на
`SyncService.state` нет: одна сетевая ошибка — и список комнат тихо перестаёт обновляться до
перезапуска приложения. Плюс приложение уходит в фон с живым sync-циклом и держит SQLite ровно в тот
момент, когда iOS будит расширение на пуш.

### M9. Неудачный restore не чистит за собой — осиротевшие зашифрованные store'ы копятся
Если `restorePreviousSession()` бросает, `restore()` глотает ошибку и уходит в `.signedOut`; ни
сессия, ни директории не удаляются. Новый вход мнёт новый `sessionID` и новые директории, а старые не
удалит уже никто — при том что `storePassphrase()` возвращает **тот же** ключ, то есть старый store
остаётся и на диске, и расшифровываемым. С учётом C1 это будет происходить не однократно.

### M10. `startSignIn` удаляет store прошлой попытки, а `pendingClient` продолжает на него указывать
`discardStore` выполняется **до** того, как новая попытка удалась. Если lookup бросил, `pendingClient`
и `pendingSessionID` указывают на предыдущую сессию, чей SQLite только что стёрли. Дальше
`signIn(username:password:)` сохранит в Keychain сессию, у которой нет стора.

### M11. `restorePreviousSession()` не ограничен таймаутом
Инвариант проекта — «каждый SDK-вызов, которого ждёт пользователь, ограничен». Здесь не так: на
запуске это **вечный `ProgressView`**. В `PushDecoder` бюджет 20 с накрывает только
`getNotification`, а restore и `notificationClient` — вне бюджета, так что обещание «20 из 30» не
выполняется.

### M12. `RoomDetailsStore.load()` — пять `try?` подряд, все ошибки проглочены
Если `roomInfo()` упал, экран показывает пустое имя, `privacy == .unknown`, ноль участников — и
**никакого** `failure`, хотя поле и алерт для него уже существуют. Дополнительно `loadAlerts()` в
этом состоянии спрашивает дефолт с `isEncrypted: false` и покажет для зашифрованной комнаты чужое
правило уведомлений.

### M13. Оптимистичные правки не реентерабельны: откат затирает более свежее значение
Шаблон `let previous = X; X = new; try await …; catch { X = previous }` в пяти местах
`RoomDetailsStore` и трёх — `UserSession`. Два `rename` подряд: B успел, потом A упал → имя
откатывается к значению **до A**, затирая успешный B. **Чинить:** CAS-откат (откатывать, только если
текущее значение всё ещё наше) или сериализация правок на поле.

### M14. `RoomListStore.scheduleRebuild`: хвост задачи обнуляет чужую регистрацию
`self?.rebuildTask = nil` в хвосте обнуляет **любой** текущий `rebuildTask`, в том числе чужой →
возможны два параллельных ребилда, оба пишут `rooms`, побеждает финиширующий последним → откат к
устаревшему списку. **Чинить:** сравнение по идентичности задачи.

### M15. `IskraRootView.body` создаёт новый `TimelineStore` на каждую перерисовку
`session.timeline(forRoomID:)` не кэширует и вызывается **прямо в `body`**. Спасает только
`@State(initialValue:)` + `.id(roomID)` — работает первый стор, остальные немедленно выбрасываются.
Сегодня это мусор и лишние FFI-вызовы; завтра, если кто-нибудь перенесёт в `init` регистрацию
листенера, каждая перерисовка начнёт открывать новый таймлайн.

### M16. Два источника правды об имени и аватаре комнаты
Шапка (`TimelineStore`) живёт на подписке и обновляется сама; экран «инфо» (`RoomDetailsStore`)
читает `roomInfo()` один раз и держит копию. Переименование с другого устройства при открытом экране
инфо не доедет туда никогда.

### M17. `RoomView.onDisappear` с guard может пропустить `stop()` при выходе из комнаты изнутри «инфо»
Если `isShowingDetails` ещё `true` в момент снятия `RoomView` («Покинуть» из экрана инфо), guard
уводит выполнение мимо `saveDraft`, `timeline.stop()`, `voice.cancel()`, `videoNote.cancel()`.
Уведомление «печатает…» тоже не отзывается.

### M18. Голосовая запись упирается в 5-минутный кэп — UI замирает
`record(forDuration: 300)` останавливает рекордер, тикер это замечает и просто выходит, **не меняя
`state`**. Микрофон выключен, а в композере полоска записи, пульсирующая точка и застывшие «5:00».
Человек продолжает говорить в никуда.

### M19. Тап-таргеты меньше 44pt
Chevron закреплённых — 16×16; крестик очистки поиска — без `frame`, ≈17pt; play голосового — 28pt.
HIG требует минимум 44×44. Комментарий у `voiceButton` защищает 28pt тем, что «пузырь целиком уже
тап-таргет», но пузырь ловит контекстное меню, а play — единственный способ включить голосовое.

### M20. Dynamic Type: текст растёт, контейнеры — нет
`@ScaledMetric` не используется **ни разу**. Размеры фиксированы: `composerControl 44`,
`searchField 44`, `waveform 24`, `avatar 40`. При AX3–AX5 шрифты вырастают в 2–3 раза, а круглые
кнопки композера остаются 44pt. Плюс `.lineLimit(1)` на названии комнаты жёстко обрежет его.

### M21. Тон: пять строк выбиваются
`sendFailure.server` (EN) говорит «homeserver» — слово, которое проект сам себе запретил (в соседнем
файле стоит комментарий «must not say 'homeserver'»); русская версия правильная.
`encryption.otherDevices` рассказывает пользователю про «библиотеку Matrix, на которой Iskra
работает». `message.spoken.*` — все в мужском роде, VoiceOver читает «Аня: отправил фото», при том что
проект уже решил ровно эту задачу нейтральными формулировками в `roomEvent.*`. Формулировки — в
`compliance-checklist.md`.

### M22. Ошибка входа не озвучивается, хотя комментарий уверен, что озвучивается
`SignInView` — `.accessibilityAddTraits(.isStaticText)` с комментарием «Announced by VoiceOver the
moment it appears». Это неверно: трейт не заставляет VoiceOver ничего произнести. Панель с ошибкой
появляется молча. **Чинить:** `AccessibilityNotification.Announcement(...).post()`.

### M23. `apply(diffs:)` в `TimelineStore` и `PinnedStore` — буквальный дубликат, ничем не покрытый
Оба держат `[TimelineItem]`, оба разбирают `[TimelineDiff]`, switch'и по 12 кейсам совпадают
посимвольно. В них живёт нетривиальная защита границ из FFI — и **ни один тест её не трогает**.
(`RoomListStore` — другой тип и другой enum; там копия намеренная, оставить.)
**Чинить:** `extension Array where Element == TimelineItem`, один тест на 12 кейсов.

### M24. `Theme` обещает «всё кратно 4» и сам себе противоречит; ~60 литералов мимо `Theme`
Внутри `Theme`: `withinRun = 2`, `recordingDot = 10`. Снаружи — `.padding(.horizontal, 7)`; три
разных затемнения (0.4 / 0.45 / 0.5) для визуально одной плашки; одна и та же кнопка play на 44 и на
40; девять `duration: 0.2` при существующем `Theme.Timing`. Ровно тот дрейф, который комментарий в
`Theme.swift` предсказывает.

### M25. Голые константы протокола и продуктовых правил
`paginateBackwards(numEvents: 25)` — размер страницы всего приложения, на который **проза в другом
файле ссылается по имени** («Ten pages of twenty-five events»); `< 300` — окно склейки сообщений в
серию; `1024` — масштаб waveform, продублирован голым в кодировании и декодировании; `count: 32` —
длина ключа; `.milliseconds(50)` — дебаунс, задокументированный в CLAUDE.md и не объявленный нигде.

### M26. `aps-environment: development` и лишний `NSPhotoLibraryUsageDescription`
Первое перед релизом должно стать `production`, иначе пуши от боевого APNs не придут. Второе —
полный доступ к фотобиблиотеке — не нужно: `PhotosPicker` не требует разрешения вообще, а сохранение
идёт через add-only с собственной строкой.

## LOW

- **L1.** `send(video:/file:/voice:/location:)` и `send(text:)` молча возвращаются при `timeline == nil` —
  человек нажал «отправить», не произошло ничего и никто ничего не сказал. (`send(photo:)` делает
  правильно: лог + `sendFailure`.)
- **L2.** `precondition` в `SessionStore.randomSecret` — падение процесса при отказе CSPRNG, в том
  числе **в notification-расширении**, где крэш = отсутствие уведомления без следа. Сигнатуры вокруг
  уже `throws`.
- **L3.** `toggleReaction` спрашивает `canReact` у `rows`, а `rows` во время refill — намеренно
  **старая** версия разговора. Реакция на уже удалённое сообщение пройдёт проверку.
- **L4.** `RoomListStore.stop()` не сбрасывает `rooms`/`isLoadingInitialRooms` — после sign-out стор
  продолжает публиковать список комнат прошлого пользователя.
- **L5.** `notificationSettings()` — гонка на кэше: два параллельных вызова создадут два объекта,
  каждый со своей регистрацией листенера (ровно то, от чего кэш заводился).
- **L6.** `NotificationService.didReceive` безусловно перетирает `pending`: если iOS переиспользует
  экземпляр для второго пуша до доставки первого, handler первого не вызовется **никогда** — тот самый
  отказ, который класс существует предотвращать.
- **L7.** `fillPages` тратит попытки на ожидание чужой страницы: `page()` при уже летящей странице
  ждёт и возвращается, ничего не загрузив, а счётчик увеличивается. На медленном сервере лимит может
  быть выбран одними ожиданиями.
- **L8.** `send(file:)` берёт имя файла пользователя (фото и видео — правильно, UUID). В шифрованной
  комнате оно внутри шифрования; но публичные комнаты **нешифрованные**, и там `паспорт_скан.pdf`
  называет себя серверу и всем читателям.
- **L9.** `spinnerRest` Task не отменяется в `onDisappear` (рядом `lighting` — отменяется).
- **L10.** `AudioPlayback`: `Timer` в `.default` runloop mode — во время скролла волна голосового
  замирает; `deinit`, инвалидирующего таймер, нет.
- **L11.** `MediaThumbnail.task(id: attachment.filename)` — идентичность по имени файла; два вложения
  с именем `image.jpg` в одной позиции не перезагрузятся. `Attachment` уже `Equatable`.
- **L12.** `TimelineStore` — единственный стор мимо общего механизма ошибок (`didFailToLoad: Bool` +
  сырой `LocalizedStringResource` вместо `ActionFailure`), из-за чего `RoomView` руками собирает
  `.alert` на 7 строк вместо `.failureAlert($…)`.
- **L13.** `MARK` отсутствуют в двух самых больших вью-файлах (`MessageRow`, `RoomInfoView`).
- **L14.** `RoomInfoView.body` — 140 строк почти без прозы (14 % комментариев против 49 % у
  `RoomView.body`): по плотности кода самое монолитное тело в базе.
- **L15.** `roomEvent.encryptionEnabled` — «сквозное шифрование» / «end-to-end encrypted» при
  декларации «no cryptography vocabulary» у соседних ключей.
- **L16.** `recording.hint` — телеграфный VoiceOver-хинт («Тап — голосовое или видео, зажать —
  запись»), который **слушают**, а не читают.
- **L17.** `RecordLock` — кастомная затемняющая заливка под стеклом; Apple прямо отговаривает
  («custom backgrounds… might interfere with Liquid Glass»).
- **L18.** `README.md`, раздел «Not built yet», устарел на три пункта из четырёх: создание комнат,
  голосовые и (наполовину) пуши давно сделаны. ROADMAP честен, README выпал из ритуала.
- **L19.** Две мелкие протечки слоёв: `SignInModel` импортирует `MatrixRustSDK` ради одного имени
  типа в приватной сигнатуре; `Attachment.source: MediaSource` — SDK-тип в публичном API `IskraCore`
  (инкапсуляция держится на дисциплине, а не на компиляторе).

## Проверено и оказалось в порядке

Чтобы не искали второй раз — это проверялось скептически и подтвердилось:

- **Своей криптографии нет.** Единственное обращение к `Security` вне Keychain —
  `SecRandomCopyBytes`. Ни `CryptoKit`, ни `CommonCrypto`, ни `CCCrypt`, ни самописных
  AES/XOR/хэшей — ноль по всей базе. Blurhash — публичная спецификация woltapp, к криптографии
  отношения не имеет.
- **Все пути отправки медиа шифруются.** `Client.uploadMedia` и `Room.sendRaw` **не вызываются
  нигде** — только упоминаются в комментариях, объясняющих, почему их нельзя.
- **Blurhash не утекает.** В зашифрованной комнате весь `content` события (включая `info.blurhash`,
  размеры, `waveform`, `geo_uri`, `filename`) шифруется целиком. Отпечаток виден серверу только в
  нешифрованных комнатах, где и так видна сама картинка.
- **TLS не трогали.** Ни одного `URLSession`, ни `serverTrust`, ни `NSAppTransportSecurity`. Вся сеть —
  внутри SDK.
- **Секреты — только в Keychain, атрибуты верные.** `AfterFirstUnlockThisDeviceOnly` +
  `kSecUseDataProtectionKeychain` + access group. `clear()` сносит секреты **раньше** файлов.
  `UserDefaults` держит только акцент, тему и быструю реакцию.
- **Границы таргетов соблюдаются.** `import SwiftUI` в `IskraCore` — 0. `MatrixRustSDK` в
  `IskraDesign` — 0.
- **NSE устроен верно.** `.multipleProcesses`, `AppIdentifierPrefix` в собственном Info.plist,
  линкует только `IskraCore`, content handler зовётся ровно один раз через `Mutex`, `userInfo` несёт
  **только** `room_id`.
- **Локализация в идеальном порядке.** Ключи en/ru совпадают точно, осиротевших нет, неиспользуемых
  нет, плюрали на месте.
- **Ноль TODO/FIXME/HACK. Ноль мёртвого кода. Ноль закомментированного кода.** Три `fatalError`/`as!` —
  все в обязательных заглушках.
- **Дисциплина Liquid Glass** — лучше, чем в большинстве живых приложений: правило не просто
  соблюдено, оно закодировано в API (нет `.glass()`, есть только `.navigationGlass()`).
- **Копирования из element-x нет.** Проверено двумя способами: построчное пересечение
  нормализованных строк ≥40 символов (68 совпадений — все общие идиомы SwiftUI/Foundation и сигнатуры,
  продиктованные FFI) и шинглы из 5 подряд идущих строк (8 совпадений — все цепочки закрывающих
  скобок). Заявление в `CLAUDE.md` подтверждается.
- **ROADMAP честен.** Всё, помеченное `[x]`, действительно сделано; открытые пункты соответствуют
  реальному отсутствию `setPusher`. (README — нет, см. L18.)
