# Промпт для Claude Code: тотальный аудит и чистка проекта Iskra

Скопируй всё, что ниже, и вставь в Claude Code в директории проекта.

---

Проведи полный аудит проекта **Iskra** — Matrix-клиента для iOS / iPadOS / macOS на Swift + SwiftUI поверх matrix-rust-sdk. Цель: довести проект до состояния, в котором он готов к релизу — без багов, с безопасной архитектурой и чистым кодом.

**Ты можешь и должен запускать субагентов** для параллельной работы по независимым направлениям аудита. Разделяй зоны ответственности так, чтобы агенты не наступали друг другу на ноги: каждому — свой участок кодовой базы или свой срез проверки. Собери их результаты в единый отчёт.

## Порядок работы

**Фаза 1 — разведка (перед любыми правками).**
Прочитай кодовую базу целиком, составь карту проекта: модули, слои, зависимости, точки входа, где живёт FFI-слой matrix-rust-sdk, где крипто, где сеть, где UI. Ничего не меняй на этом этапе. Зафиксируй карту в файле `docs/architecture-map.md`.

**Фаза 2 — параллельный аудит (субагенты).**
Запусти агентов по направлениям ниже. Каждый агент выдаёт список находок с указанием: файл, строка, серьёзность (critical / high / medium / low), в чём проблема, как чинить.

**Фаза 3 — консолидация.**
Собери все находки в единый файл `docs/audit-report.md`, отсортированный по серьёзности. Дедуплицируй пересекающиеся находки.

**Фаза 4 — починка.**
Чини по приоритету: critical → high → medium → low. Каждая логическая правка — отдельный коммит с внятным сообщением. После каждого блока правок — сборка и прогон тестов, чтобы не сломать соседнее.

**Фаза 5 — верификация.**
Финальный прогон: сборка под все три платформы (iOS / iPadOS / macOS), тесты зелёные, линтер чистый. Отчёт о том, что починено и что осознанно оставлено (с обоснованием).

## Направления аудита

### 1. Баги и корректность
- Найди и исправь все баги: краши, гонки данных, утечки памяти, retain cycles, некорректная обработка ошибок, force unwrap там, где может быть nil.
- Concurrency: проверь корректность работы со Swift Concurrency / акторами, отсутствие data races, правильность `@MainActor` на UI-слое.
- Edge cases: пустые состояния, потеря сети, невалидные ответы сервера, отмена запросов, фоновые/foreground переходы.
- Проверь покрытие тестами. Где логика критична, а тестов нет — допиши тесты.

### 2. Кибербезопасность (наивысший приоритет)
- **E2EE**: проверь, что шифрование целиком делегировано крипто-стеку matrix-rust-sdk и нигде не реализовано вручную. Никаких самописных крипто-примитивов.
- **Утечки данных**: ни при каких условиях (включая debug-сборки) в логи, крашлоги, аналитику не должны попадать содержимое сообщений, ключи, access-токены. Прогреби все `print`, `NSLog`, логгеры.
- **Хранение секретов**: access token, ключи, session data — только Keychain, с корректными access-атрибутами. Никаких UserDefaults / plaintext-файлов для чувствительных данных.
- **Сеть**: TLS-валидация не отключена, нет обходов проверки сертификатов, нет хардкоженных креденшелов или ключей в исходниках/конфигах.
- **Верификация устройств и ключей**: проверь, что реализована корректно и что нет путей, где пользователь молча получает непроверенное устройство.
- **Notification Service Extension**: расшифровка пушей идёт на устройстве, содержимое не утекает наружу; проверь sandbox и обмен данными между расширением и приложением (app group).
- **Вложения**: проверь, что медиа шифруются, что нет утечки метаданных, что временные файлы корректно очищаются.
- **Разрешения**: запрашиваются минимально необходимые, все Info.plist usage-строки на месте и внятные.

### 3. Архитектура
- Оцени слои: чёткое разделение UI / ViewModel / доменной логики / данных. Нет ли протечки FFI-типов matrix-rust-sdk прямо во View.
- Модульность: общий core переиспользуется между таргетами iOS/iPadOS/macOS, платформенная специфика изолирована.
- Управление зависимостями: нет ли синглтон-помойки, всё ли инжектится тестируемо.
- Управление состоянием и жизненным циклом сессии Matrix — корректно ли, нет ли зомби-сессий.

### 4. Чистота кода
- Мёртвый код, закомментированные блоки, дублирование, TODO/FIXME — вычистить или довести до ума.
- Единообразие стиля и неймингов по всей базе. Прогони SwiftLint / SwiftFormat (если не подключены — подключи и настрой конфиг).
- Читаемость: разбей монструозные функции и вью, вынеси магические числа в константы.
- Документируй публичные API и неочевидные места. Не документируй очевидное.

### 5. Соответствие изначальному ТЗ
Сверь текущее состояние проекта с исходным техзаданием, по которому он строился. Проверь по пунктам:
- Стек: matrix-rust-sdk через UniFFI-биндинги (не легаси matrix-ios-sdk), SwiftUI, SPM.
- Дизайн: минималистичный, округлый; стилистика в духе Telegram / iMessage; Liquid Glass применён уместно; соответствие **Apple Human Interface Guidelines** и нативной дизайн-системе — сверься с актуальной HIG-документацией, не полагайся на память.
- Accessibility: Dynamic Type, VoiceOver, светлая/тёмная тема — реально работают, а не заявлены.
- Tone of voice: все UI-тексты дружелюбные и понятные широкой аудитории, без гиковского жаргона (никаких «гомосервер», «мегольм-сессия» и т.п. в интерфейсе). Пройди по всем строкам локализации и вычисти жаргон.
- MVP-фичи на месте и работают: сообщения, комнаты, поиск по сообщениям, SSO-логин, вложения (файлы/фото/видео/голосовые), видео-«кружочки» (круглое превью, лимит 60 секунд), push-уведомления.

Составь чек-лист соответствия: пункт ТЗ → статус (сделано / частично / не сделано / сделано иначе) → что доделать.

### 6. Архитектурное соответствие element-x-ios
Сверь архитектуру Iskra с официальным клиентом **element-x-ios** (github.com/element-hq/element-x-ios) — он построен на той же matrix-rust-sdk и является эталонным референсом от команды Matrix.

Сравни по осям: интеграция с FFI-слоем, работа с timeline и синхронизацией, обработка E2EE и верификации, устройство push-пайплайна, кэширование и хранение, структура модулей.

Для каждого расхождения ответь: это осознанное упрощение (Iskra минималистичнее — ок), или это **ошибка/пробел**, который выйдет боком (особенно в крипто, синхронизации и пушах — там отклоняться от эталона опасно). Расхождения второго типа — чинить, приводя к подходу element-x.

Важно: element-x-ios под AGPL-3.0. Используй как референс архитектуры и учебный материал. Если где-то в Iskra обнаружится дословно скопированный код — пометь это отдельно и подсвети мне, чтобы я разобрался с лицензией.
