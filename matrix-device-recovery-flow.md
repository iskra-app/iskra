# Юзерфлоу: подтверждение новых устройств без крипто-жаргона

## Контекст
Клиент на matrix-rust-sdk (Swift bindings). Нужен флоу, при котором пользователь
может пользоваться е2ее-чатами на нескольких устройствах, не понимая и не видя
терминов cross-signing, secret storage, verification, megolm и т.д.

Вся механика прячется за одной сущностью — **кодом восстановления**
(recovery key), который для пользователя выглядит как обычный backup-код,
как в 2FA-приложениях.

## Терминология для UI (жёстко зафиксировать в копирайтинге)
- "recovery key" → "код восстановления"
- "secret storage" / "secure backup" → "резервная копия переписки"
- "cross-signing" / "device verification" → в UI не упоминается вообще
- "unverified device" → в идеале не показывается как угроза, максимум —
  нейтральная иконка "новое устройство", без алармистских формулировок
- глагол для действия пользователя: не "верифицировать", а "разблокировать" /
  "восстановить" переписку

## Flow 1 — первая установка приложения (аккаунт только что создан)
Триггер: успешная регистрация, устройств с историей ещё нет.

Действия:
1. Приложение в фоне включает резервное копирование и код восстановления
   (аналог "enable recovery") сразу после первого входа, без участия юзера.
2. Пользователю показывается один экран: "код восстановления" —
   с явным призывом сохранить (скопировать / показать QR / отправить себе
   в заметки). Без объяснения крипто-механики — просто "он понадобится,
   если ты зайдёшь с нового телефона или потеряешь этот".
3. Экран можно пропустить, но флоу обязан позже (например через день
   или при попытке зайти с нового устройства) напомнить, что код не сохранён.
   Важно: показать код можно только один раз, в момент создания — повторно
   его достать нельзя (это неотъемлемое свойство secret storage в matrix,
   а не ограничение UX). Если юзер его не сохранил — единственный путь
   назад — сгенерировать новый код, см. "Управление кодом восстановления".

## Flow 2 — вход с нового устройства, на аккаунте уже настроено восстановление
Триггер: логин на устройстве, где ещё нет локального крипто-стора,
а на сервере у аккаунта уже есть настроенное восстановление.

Действия:
1. После обычного логина (логин/пароль или токен) — экран с выбором из
   двух равнозначных кнопок, без деления на "основной"/"запасной" способ:
   - "у меня есть код восстановления"
   - "подтвердить с другого устройства"
2. Ветка "код восстановления": один инпут, "введи код восстановления,
   чтобы получить доступ к своим чатам". После ввода корректного кода —
   устройство прозрачно получает доступ к истории и считается доверенным.
   Если код неверный — "код не подошёл, проверь и попробуй ещё раз" плюс
   ссылка на Flow 4 ("не могу найти код").
3. Ветка "подтвердить с другого устройства": по сути emoji/QR-сверка
   (SAS), но в упрощённой обёртке — "открой приложение на своём другом
   телефоне, там появится запрос на подтверждение" → набор эмодзи/картинок
   для сравнения на обоих экранах, без слов "verification"/"SAS"/"cross-
   signing". После подтверждения устройство считается доверенным и
   получает доступ к истории (через key gossiping / доверенных участников).
4. Если у пользователя нет ни кода восстановления, ни другого
   залогиненного устройства под рукой — с любого из двух экранов должен
   быть явный выход в Flow 4 ("нет доступа ни к тому, ни к другому").

## Flow 3 — пользователь потерял код восстановления
Триггер: юзер на экране ввода кода жмёт "не могу найти код" (или сразу
попадает сюда с экрана выбора, если ни один из двух вариантов недоступен).

Действия:
1. Если есть другое залогиненное устройство — предложить ветку
   "подтвердить с другого устройства" из Flow 2 как способ восстановить
   доступ, и сразу после подтверждения сгенерировать новый код
   восстановления взамен утерянного.
2. Если других устройств нет — явно и без запугивания объяснить: старая
   переписка восстановлению не подлежит, начнётся "чистая" история;
   после входа сразу сгенерировать новый код восстановления и провести
   через Flow 1.
3. Не предлагать сброс через email/пароль как способ вернуть старые
   сообщения — это разные вещи (сброс пароля аккаунта не равно
   восстановлению ключей шифрования), нужно явно развести эти два сценария
   в самом флоу, чтобы разработчик не перепутал их местами.

## Управление кодом восстановления (настройки аккаунта)
- показать текущий статус: "резервная копия включена" / "не включена"
- возможность сгенерировать новый код взамен старого (старый после этого
  должен переставать работать — явно предупредить об этом в UI, показать
  новый код ровно один раз в момент генерации)
- список устройств: показывать по-человечески ("iPhone Ани, последний раз
  онлайн вчера"), без технических деталей вроде device id/ключей;
  разлогин чужого/утерянного устройства — отдельная кнопка в этом же месте

## Не входит в этот флоу (сознательно исключено)
- скрытие emoji-подтверждения как второсортного/запасного варианта —
  на экране входа обе кнопки равнозначны
- повторный показ кода восстановления после того как он один раз был
  показан пользователю
- отображение предупреждающих "щитов" о недоверенных устройствах как
  блокирующий элемент интерфейса переписки
- любые упоминания crypto-терминов в пользовательских текстах

## Критерии готовности
- новый пользователь никогда не видит слов verification/cross-signing/
  secret storage/backup key в интерфейсе — только "код восстановления" и
  "резервная копия переписки"
- вход с нового устройства сразу предлагает выбор из двух равнозначных
  способов (код восстановления / подтверждение с другого устройства),
  без навязывания одного как основного
- потеря кода восстановления не блокирует юзера намертво — есть понятный
  путь либо через другое устройство, либо через явный "старт с чистого листа"
