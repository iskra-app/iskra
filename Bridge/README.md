# Iskra bridge — matrix через nostr

Клиент, который не может достучаться до своего homeserver'а напрямую, заворачивает каждый HTTP-запрос
в зашифрованное nostr-событие и публикует его на relay. Этот сервис слушает те же relay,
разворачивает запрос обратно, делает его к настоящему homeserver'у и тем же путём возвращает ответ.
Для сети между человеком и relay это выглядит как nostr — потому что это и есть nostr.

Это часть проекта [Iskra](../README.md); клиентская сторона живёт в том же репозитории.

## Прежде всего: что бридж видит

**Бридж терминирует Matrix Client-Server API.** Значит, он видит:

- access token человека — он приходит в заголовке `Authorization`;
- все room id и event id, кто кому пишет и когда;
- **тела сообщений в незашифрованных комнатах.**

Чего он не видит — содержимого зашифрованных комнат: Olm и Megolm живут выше этого слоя, ключи от
них есть только у устройств. Но всё остальное перед бриджем открыто, и это не изъян реализации, а
устройство схемы: чтобы переписать HTTP-запрос, его надо прочитать.

Отсюда правило: **бридж поднимают себе, а не пользуются чужим.** Чужой бридж — это чужой человек с
вашим access token'ом. По той же причине в логах нет ни тел, ни заголовков, ни полных путей (в пути
лежат room id и event id) — только метод, первые два сегмента пути, статус, размеры и pubkey
клиента, и ровно столько, сколько нужно для rate limit.

Токены нигде не сохраняются: бридж не пишет на диск вообще ничего.

## Запуск

```sh
docker build -t iskra-bridge .
docker run --rm \
  -e ALLOWED_UPSTREAMS=matrix.example.org \
  -e BRIDGE_NOSTR_PRIVKEY=nsec1... \
  -e RELAY_LIST=wss://relay.damus.io,wss://nos.lol \
  iskra-bridge
```

Ключ — 32 случайных байта; годится и hex, и `nsec`:

```sh
openssl rand -hex 32
```

**Свой pubkey бридж печатает при старте** (`bridge is listening pubkey=...`) — это то, что нужно
вписать в клиент.

### Переменные окружения

| Переменная | Обязательна | По умолчанию | Что делает |
|---|---|---|---|
| `ALLOWED_UPSTREAMS` | да\* | — | Хоумсерверы, на которые бридж согласен ходить, через запятую. `*` — любой публичный. |
| `HOMESERVER_URL` | да\* | — | Куда идёт запрос, не назвавший сервер. Если `ALLOWED_UPSTREAMS` не задан — единственный разрешённый. |
| `BRIDGE_NOSTR_PRIVKEY` | да | — | Секретный ключ бриджа, `nsec` или hex. |
| `RELAY_LIST` | да | — | Relay, которые бридж слушает, через запятую. `ws://`/`wss://`. |
| `CLIENT_RELAY_LIST` | нет | `RELAY_LIST` | Что бридж рекомендует клиентам. Отдельно — чтобы менять список у клиентов, не трогая свои подключения. |
| `RATE_LIMIT_PER_MIN` | нет | `120` | Запросов в минуту на один pubkey клиента. |
| `ALLOWED_PUBKEYS` | нет | пусто | Если задан — обслуживаются только эти ключи. Пусто = открытый бридж. |
| `MAX_BODY_CHUNK` | нет | `24576` | Сырых байт тела на один чанк. |
| `REQUEST_TIMEOUT_SECS` | нет | `60` | Сколько бридж ждёт homeserver. |
| `RUST_LOG` | нет | `info` | Уровень логов. |

\* Нужна хотя бы одна из двух. Мост, которому некуда ходить, не запускается.

Неверная конфигурация — это отказ запуститься, а не проблема, которая всплывёт на первом запросе:
бридж, узнающий на живом трафике, что его `HOMESERVER_URL` — не URL, уже принял запросы, которые не
может обслужить.

## Какие хоумсерверы обслуживает мост

Целевой сервер едет **в запросе**, а не в конфиге. Иначе и быть не может: при входе SDK спрашивает
`/.well-known/matrix/client` у `matrix.org`, а всё после discovery шлёт на
`matrix-client.matrix.org` — два разных хоста в рамках одного аккаунта. Мост, прибитый к одному
адресу, не обслуживает толком даже его.

Конфиг решает не «куда», а «куда можно»:

```sh
# мост для одного сообщества
ALLOWED_UPSTREAMS='example.org,matrix.example.org'

# мост для matrix.org
ALLOWED_UPSTREAMS='matrix.org,matrix-client.matrix.org'

# публичный мост: любой публичный хоумсервер
ALLOWED_UPSTREAMS='*'
```

Запись свободная: `matrix.org`, `https://matrix.org`, `https://matrix.org/` — это одно и то же,
сравниваются origin'ы, а не строки. Без схемы подразумевается `https`.

Три отказа, и каждый из них — это то, чем мост иначе бы стал:

- **Не Matrix-путь.** Пропускаются только `/_matrix/…` и `/.well-known/matrix/…`. Без этого мост —
  анонимная веб-прокся, которая по случайности говорит на nostr. Проверяется при этом не строка,
  которую прислал клиент, а собранный URL: `..` становится сегментом каталога только когда есть
  база, к которой его приклеили, поэтому `/_matrix/../admin/secrets` проходит проверку по префиксу
  и превращается в `/admin/secrets` ровно в тот момент, когда URL наконец собирают. Мост собирает
  URL первым и судит вторым — так проверяемое и запрашиваемое это один и тот же объект.
- **Не публичный адрес** (только при `*`). `http://192.168.1.1/`, `http://169.254.169.254/`,
  `http://127.0.0.1:8080/` — открытый мост, который сходит по такому адресу, это сканер локальной
  сети оператора. Имя резолвится, а не просто осматривается; полностью DNS rebinding это не
  закрывает, и тому, кого такой зазор не устраивает, стоит перечислить сервера списком вместо `*`.
  Перечисленный сервер проверку адреса не проходит — она ему не нужна: оператор за него поручился,
  и его собственный хоумсервер вполне может стоять в той же приватной сети.
- **Не в списке.** Отказ приходит клиенту как `403`, а не тишиной: клиент должен уметь отличить
  «этот мост не обслуживает твой сервер» от «мост умер».

Открытый мост (`*`) говорит об этом предупреждением в лог при каждом старте — это решение, и
расплачивается за него трафиком и репутацией оператор.

## Закрытый бридж

`ALLOWED_PUBKEYS` превращает бридж в приватный: обслуживаются только перечисленные ключи, остальные
не получают даже ошибки — просто тишину. Открытый бридж (переменная не задана) держится на одном
`RATE_LIMIT_PER_MIN`, и его публичный ключ по природе своей публичен, так что рассчитывать стоит на
то, что им воспользуется кто угодно.

## Проверка

```sh
cargo test --workspace          # включая сквозной тест: relay и homeserver поднимаются в процессе
cargo clippy --workspace --all-targets
```

Сквозной тест (`crates/iskra-bridge/tests/end_to_end.rs`) — главное, что тут есть. Он поднимает
relay через `nostr-relay-builder`, homeserver через `wiremock`, берёт настоящего клиента из
`iskra-tunnel-probe` и проверяет, что запрос, ушедший nostr-событием, возвращается байтами
homeserver'а. Никакого задеплоенного бриджа и никакой сети для этого не нужно.

Против живого сервера — тот же клиент одной командой:

```sh
PROBE_UPSTREAM=https://matrix-client.matrix.org \
BRIDGE_PUBKEY=<pubkey из лога бриджа> \
RELAY_LIST=wss://relay.damus.io \
cargo run -p iskra-tunnel-probe -- GET /_matrix/client/versions
```

`PROBE_UPSTREAM` тут не украшение: сервер едет в запросе, и мосту, запущенному без
`HOMESERVER_URL`, запрос без адреса идти некуда — он отвечает `403` и пишет в лог `reason="no
target"`.

Если печатается список версий Matrix — туннель работает.

## Устройство

```
crates/
  iskra-tunnel-proto/   формат на проводе: конверт, NIP-44. Без единого сетевого вызова.
  iskra-bridge/         config · listener (nostr) · forwarder (http) · ratelimit
  iskra-tunnel-probe/   клиентская сторона одной командой; ей же пользуется сквозной тест
```

`iskra-tunnel-proto` линкуется **обеими** сторонами туннеля, и это главное решение в раскладке:
клиент, который режет тело на чанки одним способом, и бридж, который собирает их другим, ломались бы
только под нагрузкой, только иногда и только в проде. Здесь один чанкер и один реассемблер, а его
юнит-тесты и есть спецификация протокола.

### События

| kind | направление | смысл |
|---|---|---|
| 20001 | клиент → бридж | чанк запроса |
| 20002 | бридж → клиент | чанк ответа |
| 20003 | клиент → бридж | подписка на sync и keepalive |
| 20004 | бридж → клиент | дельта sync, которую клиент не запрашивал |
| 20005 | бридж → клиент | список relay и размер чанка |

Всё в диапазоне 20000–29999: это эфемерные события, relay их не хранит, и хранить их незачем — обе
стороны онлайн, а туннель, оставляющий следы на чужом relay, противоречит сам себе.

**В открытых тегах только `#p` с ключом получателя.** Идентификатор запроса лежит *внутри*
шифрованного content, а не в теге: тег виден relay и склеил бы запрос с ответом для любого
наблюдателя. Цена — бриджу приходится расшифровать каждое входящее событие, чтобы узнать id; это
дёшево.

### Размер чанка

NIP-44 v2 отказывается шифровать больше 65535 байт за раз, и весь бюджет чанка считается от этого
числа, а не от круглого: круглое число, которое случайно его превышает, даёт туннель, работающий
ровно до первого длинного сообщения. 24 КиБ тела → base64 (+⅓) → JSON-конверт → base64 шифротекста
(+⅓) ≈ 44 КБ событие, что помещается в лимит 64 КБ, обычный для публичных relay.

## Клиент в приложении

Вторая половина туннеля живёт в `Sources/IskraCore/Transport/Nostr/` и говорит на том же
протоколе: тот же конверт, тот же NIP-44, те же kind'ы. `NostrTunnelUpstream` — это `HTTPUpstream`,
то есть он встаёт ровно туда, где стоял `DirectUpstream`, за тем же локальным слушателем, и выше
транспорта никто о нём не знает.

Адрес моста вписывают в приложении: **Настройки → Соединение → Адрес моста**, `npub1…` или hex —
та самая строка, которую мост печатает при старте. Там же список relay (пусто — возьмутся три по
умолчанию), ключ самого устройства (его вписывают в `ALLOWED_PUBKEYS` закрытому мосту) и кнопка
«Проверить мост», которая гоняет один настоящий запрос и говорит, что именно не так.

**Переключатель с вписанным адресом больше не откатывается на прямое соединение.** Пока на той
стороне ничего не было, откат ничего не стоил — это было ровно то же самое, что и без
переключателя. Теперь это решение о том, кто видит трафик, и молча пойти напрямую значило бы
ответить на этот вопрос за человека: не поднялся туннель — `AuthenticationError.bridgeUnavailable`,
и на экране написано, что не вышло.

Что проверено чем:

| Что | Чем |
|---|---|
| NIP-44 — тот же самый | `NIP44Tests` против официального вектор-файла NIP: ключи разговора, ключи сообщения, паддинг, целые payload'ы и сообщение на 65535 байт |
| Конверт — той же формы | `NostrTunnelTests`: JSON пришпилен как текст, включая `body_chunk` |
| Чанкинг — той же арифметики | `TunnelChunkingTests` — те же случаи, что у `chunk.rs`/`reassemble.rs`, случай в случай |
| Событие — своё | id пересчитывается из сериализации, подпись проверяется |
| Что обе половины сходятся | `LiveBridgeTests` против живого моста — по просьбе, а не по умолчанию |

```sh
cd Bridge && ./run-local.sh            # печатает `bridge is listening pubkey=…`
ISKRA_BRIDGE_PUBKEY=<этот ключ> swift test --filter LiveBridgeTests
```

Та же сделка, что и со стресс-тестами: обычный `swift test` остаётся без сети, а живая проверка —
в одну команду. Внутри приложения то же самое делает `Iskra --probe-bridge [npub] [сервер]`: он
разделяет пять отказов, которые изнутри выглядят одинаково (не тот ключ, мост не запущен, мост не
обслуживает этот сервер, закрытый мост не знает про это устройство, relay не отвечают).

Криптография на этой стороне — libsecp256k1 (пакет `21-DOT-DEV/swift-secp256k1`) плюс CryptoKit.
Сам ChaCha20 выписан руками ровно потому, что CryptoKit его не отдаёт: у него есть только AEAD
`ChaChaPoly`, который приклеивает свой Poly1305 и голый поток наружу не показывает, а NIP-44 нужен
именно голый — с собственным HMAC. Двадцать строк, и вектор-файл проходит через них на каждом
шифровании.

## Длинные тела: чанкинг

NIP-44 отказывается шифровать больше 65535 байт за раз, а публичные relay обычно не принимают
событие больше 64 КБ — так что одно событие несёт 24 КиБ тела, и это потолок, из которого исходит
всё остальное. Сообщение длиннее режется на конверты: `chunk.rs` режет, `reassemble.rs` собирает,
и обе половины туннеля линкуют один и тот же код, а Swift-сторона (`TunnelChunker`,
`TunnelReassembler`) держится теми же тестами, случай в случай.

Правил ровно три, и каждое из них — это баг, который иначе всплывает только под нагрузкой:

- **Голова едет только на нулевом чанке.** `method`, `path`, `headers`, `upstream`, `status` — там
  и больше нигде; конверт с ними на любом другом месте отвергают обе стороны. Повторять их на
  каждом чанке значило бы платить за них байтами при потолке в 64 КБ.
- **Порядок не гарантирован, дубликаты — норма.** Событие уходит на все relay и приходит со всех,
  так что один и тот же чанк приезжает несколько раз, а седьмой вполне может опередить нулевой.
  Сборщик считает каждый чанк один раз и не ждёт голову первой.
- **Недособранное лежит в памяти, поэтому оно ограничено**: 512 чанков, 8 МБ на сообщение, 64
  недособранных сообщения сразу, 60 секунд на каждое. Мост без этих потолков — это мост, который
  любой желающий кладёт, начав десять тысяч сообщений и не закончив ни одного. На телефоне то же
  самое, только память чужая.

Пустое тело — это **один** чанк, а не ноль: запрос без тела всё ещё запрос.

Сколько это стоит, на relay и хоумсервере в одном процессе (`cargo test --release --test stress --
--ignored`):

| Тело | Чанков | Время |
|---|---|---|
| 24 КиБ | 1 | 6 мс |
| 200 КБ | 9 | 17 мс |
| 1 МБ | 43 | 53 мс |
| 4 МБ | 171 | 143 мс |

Через публичные relay так гонять не стоит — 171 событие ради одного ответа это то, за что
волонтёрский relay вправе отключить кому угодно. Для медиа это довод за свой relay, а не за
терпение чужого.

## Целая сессия через мост, и сколько она стоит

`LiveBridgeSessionTests` гоняет настоящий SDK через настоящий мост и публичные relay до
демо-хоумсервера, который живёт внутри приложения: вход, sliding sync до полного списка чатов,
открыть комнату, отправить сообщение, дождаться ответа собеседника, подгрузить страницу истории.
Та же сессия идёт ещё раз напрямую, так что разница — это цена туннеля и ничего больше.

```sh
(cd Bridge && cargo build -p iskra-bridge)
ISKRA_LIVE_BRIDGE_SESSION=1 swift test --filter LiveBridgeSessionTests
```

Мост тест поднимает сам, потому что должен: мосту нужно разрешить ровно тот порт, который
слушатель выбрал при запуске.

| | напрямую | через мост |
|---|---|---|
| вход | 0,20 с | 0,93 с |
| список чатов | 0,12 с | 1,0 с |
| сообщение ушло | 0,06 с | 0,45 с |
| ответ собеседника пришёл | 1,12 с | 1,25 с |
| страница истории | 0,12 с | 0,41 с |

Одиночный запрос стоит 200–350 мс, и это цена relay, а не кода: на relay в одном процессе те же
запросы укладываются в единицы миллисекунд.

### Что нашёл первый замер

**Список чатов появлялся за 20,8 секунды.** Медленными были ровно два запроса — первые sync, чей
ответ (53 КБ) едет тремя чанками; даже `timeout=0`, на который сервер отвечает сразу, шёл 20 с.
Причина — в nostr-sdk: `send_event` возвращается не когда событие ушло, а когда **каждый** relay
пула ответил `OK` или истёк таймаут, а для лежащего relay это 10 секунд (`WAIT_FOR_OK_TIMEOUT`). Мост
слал чанки по очереди, и второй ждал, пока первый отзовётся с мёртвого relay, третий — ещё десять.
Одночанковый ответ этого не показывал никогда: клиент получает событие с живого relay задолго до
того, как мёртвый будет брошен, — поэтому ни один тест на один запрос этого не видел.

Теперь чанки уходят все сразу, с обеих сторон, а клиент пробы ждёт ответа, а не подтверждений.
`a_dead_relay_does_not_hold_up_a_chunked_answer` держит это на relay в одном процессе с мёртвым
соседом в списке, и без исправления падает.

### И почему агрегатора sync не будет — пока

Он планировался на допущении, что `/sync` через relay — это раунд-трип на каждый цикл. Замер
говорит другое: SDK держит sliding sync long-poll'ом до 30 секунд, и новое сообщение приходит
**одной дорогой в одну сторону**, как только сервер его отдал, — в таблице это «ответ пришёл», на
130 мс позже прямого соединения. Агрегатор сэкономил бы запросную половину пути только для событий,
пришедших в ~300-мс окно между ответом и следующим запросом, — ценой того, что мост вёл бы sync от
имени человека сам, с его токеном, и держал бы позиции sliding sync, чью семантику повтора сервер
понимает по-своему. Выигрыш в доли секунды не стоит ни того, ни другого.

Где туннель действительно чувствуется — это последовательные запросы: вход, первый sync, открытие
комнаты. Там каждый шаг — 200–350 мс, и уменьшить это можно только тем, что relay ближе и быстрее.

## Сколько это стоит по времени

Замерено, а не предположено: бридж на ноутбуке, `HOMESERVER_URL=https://matrix-client.matrix.org`,
`GET /_matrix/client/versions` подряд одним свежим ключом. Время — полный путь
клиент → relay → бридж → matrix.org → бридж → relay → клиент.

| Relay | min | median | max |
|---|---|---|---|
| три сразу (damus + nos.lol + primal), 20 запросов | 259 мс | **355 мс** | 1.15 с |
| `relay.primal.net`, 10 запросов | 283 мс | 364 мс | 987 мс |
| `nos.lol`, 10 запросов | 268 мс | 414 мс | 1.27 с |
| `relay.damus.io`, 10 запросов | — | — | **не отвечает** |

Первый запрос в каждой серии — около секунды: в него входят TLS-рукопожатия и websocket-апгрейды.
Установившийся round-trip — **примерно 350 мс**.

Три вывода, и третий важнее первых двух.

**Публичные relay эту нагрузку берут.** Двадцать запросов подряд от незнакомого pubkey не
притормозил никто. Полагаться на это не стоит, но запасным путём они работают.

**350 мс на запрос — причина, по которой sync-агрегатор идёт раньше клиентской части.** Matrix
болтлив, и `/sync` раунд-трипом через relay на каждый цикл превратил бы мессенджер в переписку по
телеграфу.

**Relay отваливаются, и это нормальный режим работы, а не авария.** `relay.damus.io` в момент
замера отвечал `503 Service Unavailable` на само подключение — при этом в серии «три сразу» он
входил в список, и ни один запрос не потерялся. Так и задумано: `send_event` в nostr-sdk публикует
событие **на все** relay пула, ответ приходит с того, который оказался быстрее, а дубликаты
отбрасываются по id запроса. Поэтому список из нескольких relay — не запас на будущее, а рабочий
механизм, и клиенту нужен список длиннее одного даже в идеальном мире.

Повторить замер (`PROBE_REPEAT` — сколько запросов подряд):

```sh
PROBE_REPEAT=20 BRIDGE_PUBKEY=<из лога> RELAY_LIST=wss://nos.lol,wss://relay.primal.net \
  cargo run -p iskra-tunnel-probe -- GET /_matrix/client/versions
```

## Стресс

Тяжёлая нагрузка живёт в `crates/iskra-bridge/tests/stress.rs`, против relay и homeserver'а в том
же процессе. Все тесты помечены `#[ignore]`, поэтому обычный `cargo test` остаётся трёхсекундным:

```sh
cargo test --release --test stress -- --ignored --nocapture
SOAK_SECS=300 cargo test --release --test stress -- --ignored --nocapture soak
```

Это осознанная граница: относить тысячи запросов в минуту на волонтёрский публичный relay — атака,
как её ни называй. Локальный relay терпит что угодно, публичные проверяются временем, а не напором.

Результаты на M-ноутбуке:

| Что | Итог |
|---|---|
| 3200 запросов, 32 параллельных клиента | 318 мс на всё, ~10 000 req/s, p50 3.2 мс, p99 6.6 мс |
| 60 секунд ровной нагрузки, 3001 запрос | 0 потерь, дрейфа нет (первая десятая 2.52 мс → последняя 2.60 мс) |
| 60 разных pubkey × 10 запросов | все обслужены |
| Флуд с одного ключа под потолком 30/мин | 46 пропущено, остальное отсечено, посторонний клиент не задет |
| Тела 24 КиБ · 200 КБ · 1 МБ · 4 МБ | доходят байт в байт, 6 / 17 / 53 / 143 мс |
| Четыре ответа по 300 КБ одновременно | не перепутались: каждый байт из своего ответа |

Живой прогон: 120 запросов за минуту через `nos.lol` + `relay.primal.net` до matrix.org —
**120 из 120 успешно**, медиана 333 мс, ни одного предупреждения в логе бриджа.

### Что стресс нашёл

**`while let Ok(..) = notifications.recv().await` — ловушка, и она стоила бы бриджа.** Уведомления
приходят по bounded broadcast-каналу; при переполнении `recv` отдаёт `Lagged`, и очевидная запись
через `while let Ok` **выходит из цикла**. Бридж после одного всплеска трафика замолкал бы навсегда —
оставаясь подключённым, подписанным и совершенно здоровым на вид в логах. Теперь `Lagged` — это
предупреждение и `continue`, а выход только по `Closed`. То же самое на клиентской стороне.

**Ответ, не влезающий в один конверт NIP-44, отвечал тишиной.** `seal` возвращал `TooLarge`, ошибка
уходила в лог, и клиент ждал собственный таймаут, не имея способа отличить большой ответ от мёртвого
бриджа. Сначала это стало честным 502, а с приходом чанкинга — просто ответом. 502 остался ровно для
одного случая, который резать нечем: голова, в которой одни только заголовки хоумсервера длиннее
целого конверта.

**Клиент держал по приёмнику уведомлений на каждый запрос.** При N запросах в полёте каждый видел
трафик всех остальных: работа квадратична по числу запросов, канал переполняется, и пришедший ответ
некому сопоставить с ждущим его запросом. Теперь одна задача-диспетчер разбирает поток и отдаёт
каждый ответ тому единственному, кто ждёт его id. Swift-клиент будет устроен так же.

**У `RelayBuilder::default()` потолок — 60 событий в минуту.** В тестах он поднят, потому что там он
мешает мерить бридж. Но само число стоит запомнить: это правдоподобная настройка живого relay, а
туннель тратит два события на запрос — то есть такой relay ограничивает клиента примерно тридцатью
запросами в минуту. Ещё один довод за sync-агрегатор: важна не скорость одного запроса, а то,
сколько запросов приходится делать.
