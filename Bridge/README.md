# Iskra bridge — matrix через nostr

Клиент, который не может достучаться до своего homeserver'а напрямую, открывает к нему TCP-поток
через nostr: каждый кусок потока — зашифрованное nostr-событие на relay. Этот сервис слушает те же
relay, подключается к хоумсерверу, который назвал клиент, и перекладывает байты в обе стороны. Для
сети между человеком и relay это выглядит как nostr — потому что это и есть nostr.

Это часть проекта [Iskra](../README.md); клиентская сторона живёт в том же репозитории.

## Прежде всего: что бридж видит

**Бридж не может прочитать то, что везёт.** TLS до хоумсервера делает сам Matrix SDK, с проверкой
настоящего сертификата, а через мост идёт уже шифротекст. Рассуждения и план — в
[`docs/BLIND-BRIDGE.md`](../docs/BLIND-BRIDGE.md).

| | Бридж |
|---|---|
| Access token, пароль, refresh token | не видит |
| Пути запросов, room id, event id | не видит |
| Тела сообщений и медиа — в том числе в незашифрованных комнатах | не видит |
| К какому хоумсерверу | видит (хост из `open` и SNI) |
| Когда и сколько байт | видит |
| Ключ клиента в nostr | видит |
| IP человека | не видит (его видят relay) |

Последние строки — это всё, что остаётся, и ровно это написано на экране. В логах — поток открыт,
закрыт, сколько байт, сколько жил и причина одним словом. Хоста нет даже в отказах.

(Раньше у моста был протокол, который разворачивал HTTP-запросы и поэтому читал их, токен
включительно. Его больше нет ни в мосте, ни в приложении, и откатиться на него некуда.)

Токены нигде не сохраняются — их у моста просто нет. Единственное, что бридж пишет на диск, —
собственный ключ, и только если ему дали для этого место (`BRIDGE_KEY_FILE`).

## Поставить мост

Нужен компьютер, который включён всегда и откуда открывается ваш Matrix-сервер: VPS, Raspberry Pi,
NAS, старый ноутбук. Белый IP и проброс портов не нужны: мост сам подключается к relay, поэтому
работает за любым роутером. На нём должен быть Docker (на Synology и Unraid он ставится из
пакетов, на Linux это `curl -fsSL https://get.docker.com | sh`).

**1. Скачать два файла** в пустую папку: [`docker-compose.yml`](docker-compose.yml) и
[`.env.example`](.env.example). Второй переименовать в `.env`.

**2. Вписать в `.env` свой сервер**, если это не matrix.org. Обычно адресов два: имя из Matrix ID и
адрес, где на самом деле живёт API. Для `@me:example.org` это часто
`ALLOWED_UPSTREAMS=example.org,matrix.example.org`. Всё остальное можно не трогать.

**3. Запустить:**

```sh
docker compose up -d
docker compose logs bridge | grep "bridge address"
```

Вторая команда печатает строку `bridge address for Iskra: npub1…`. Это адрес моста, его вставляют в
приложение: Настройки → Соединение → «Адрес моста». Там же есть кнопка «Проверить мост».

**4. Закрыть мост для чужих** (желательно). В приложении, на том же экране, есть «Ключ этого
устройства». Скопируйте его в `.env` как `ALLOWED_PUBKEYS=npub1…` (несколько устройств через
запятую) и выполните `docker compose up -d` ещё раз. После этого мост не отвечает никому, кроме
перечисленных.

Обновить — `docker compose pull && docker compose up -d`. Адрес при этом не меняется: ключ хранится
в томе `bridge-data`, мост создаёт его при первом запуске. **Если удалить том, у моста будет новый
адрес**, и его придётся заново вписать на всех устройствах. Перенести мост на другую машину можно
вместе с ключом: он лежит в томе в файле `bridge-key`.

Образ собран для amd64 и arm64. Тег `latest` берётся из `main`, `dev` из `dev`, а `1.2.3` — из
git-тега `bridge-v1.2.3`. Собрать образ у себя из исходников: `docker compose up -d --build`.

### Без Docker

`./run-local.sh` собирает и запускает мост через `cargo`. Ключ он создаёт сам и кладёт в
`.bridge-key` рядом со скриптом.

### Переменные окружения

| Переменная | Обязательна | По умолчанию | Что делает |
|---|---|---|---|
| `ALLOWED_UPSTREAMS` | да | — | Хоумсерверы, к которым мост согласен открывать потоки, через запятую, только `https`. `*` — любой публичный Matrix-сервер. |
| `BRIDGE_NOSTR_PRIVKEY` | да\* | — | Секретный ключ бриджа, `nsec` или hex. |
| `BRIDGE_KEY_FILE` | да\* | в образе `/data/bridge-key` | Файл с ключом. Если файла нет, бридж создаёт его сам (права `600`) и дальше читает. Если в файле не ключ, бридж не запускается, а файл не трогает. |
| `RELAY_LIST` | нет | `nos.lol`, `relay.primal.net`, `relay.nostr.band` | Relay, которые бридж слушает, через запятую. `ws://`/`wss://`. По умолчанию те же три, что приложение берёт при пустом поле. |
| `CLIENT_RELAY_LIST` | нет | `RELAY_LIST` | Что бридж рекомендует клиентам. Отдельно — чтобы менять список у клиентов, не трогая свои подключения. |
| `ALLOWED_PUBKEYS` | нет | пусто | Если задан — обслуживаются только эти ключи. Пусто = открытый бридж. |
| `MAX_STREAMS_PER_CLIENT` | нет | `16` | Потоков на один pubkey клиента. Сверх — `rst` «busy». |
| `MAX_STREAMS` | нет | `2048` | Потоков всего. Сверх — `rst` «busy». |
| `STREAM_BYTES_PER_MIN` | нет | `67108864` (64 МиБ) | Байт в минуту на клиента, в обе стороны. Сверх — поток замедляется (мост перестаёт читать и подтверждать), а не рвётся. |
| `STREAM_BYTES_PER_MIN_TOTAL` | нет | без потолка | То же на всех вместе — по ширине канала хоста. |
| `EVENTS_PER_MIN` | нет | `8192` | Событий в минуту на клиента, до расшифровки. Сверх — тишина: без расшифровки отвечать не на что. |
| `SEGMENT_BYTES` | нет | `24576` | Байт потока в одном событии. Больше нельзя: не влезет в NIP-44. |
| `POW_DIFFICULTY` | нет | `16` | Сколько бит доказательства работы (NIP-13) должно быть у `open`. `0` — выключено, больше `24` — отказ запуститься: клиенты больше 24 не майнят. |
| `RUST_LOG` | нет | `info` | Уровень логов. |

\* Нужна одна из двух. Если заданы обе, побеждает `BRIDGE_NOSTR_PRIVKEY`.

`HOMESERVER_URL`, `RATE_LIMIT_PER_MIN`, `REQUEST_TIMEOUT_SECS`, `MAX_BODY_CHUNK` и `BLIND_ONLY`
больше не читаются; мост, которому их задали, говорит об этом в лог при старте. Задан только
`HOMESERVER_URL` без `ALLOWED_UPSTREAMS` — мост не запускается и говорит, что вписать вместо.

Неверная конфигурация — это отказ запуститься, а не проблема, которая всплывёт на первом потоке.

## Какие хоумсерверы обслуживает мост

Сервер называет **клиент**, в `open`, а конфиг решает, куда можно. Иначе нельзя: при входе SDK
спрашивает `/.well-known/matrix/client` у `matrix.org`, а всё после discovery шлёт на
`matrix-client.matrix.org` — два разных хоста в рамках одного аккаунта.

```sh
# мост для одного сообщества
ALLOWED_UPSTREAMS='example.org,matrix.example.org'

# мост для matrix.org
ALLOWED_UPSTREAMS='matrix.org,matrix-client.matrix.org'

# публичный мост: любой публичный Matrix-сервер
ALLOWED_UPSTREAMS='*'
```

Запись свободная: `matrix.org`, `https://matrix.org`, `https://matrix.org/` — одно и то же,
сравниваются origin'ы, а не строки. Без схемы подразумевается `https`; `http` — отказ запуститься:
у `http`-сервера нет TLS, к которому мост был бы слеп. Хост на нестандартном порту пишут с портом:
`matrix.example.org:8448`.

Пути мост не видит, поэтому «это Matrix» решается по **хосту**:

- **только порт 443** — или тот, что указан у хоста в списке; иначе «bad port». Открытый 25-й или
  22-й — это то, за что оператора отключает хостер;
- при списке — **только хосты из списка**. Перечисленный хост — решение оператора, и частный адрес
  тоже: его собственный хоумсервер вполне может стоять в той же сети;
- при `*` — **только публичные адреса**, все до одного («not public»), и **только Matrix-серверы**:
  мост сам спрашивает хост своим TLS, на тех же адресах, `GET /_matrix/client/versions` (JSON с
  массивом `versions`) или `GET /.well-known/matrix/client` (JSON с `m.homeserver`). Ответ помнится
  **по адресу**, а не по имени, — «да» сутки, «нет» десять минут, — и поток идёт только на адреса,
  сами ответившие «да». Иначе имя, однажды ответившее со своего сервера, после смены DNS сутки
  водило бы через мост на чужой IP: клиент приносит свой TLS, и чужой сертификат его не остановит.
  Проверка сама не должна стать оружием: не больше двух адресов на один `open`, имя больше чем с 16
  адресами — отказ, 10 проверок в минуту на клиента и 120 на всех (сверх — «busy»); запомненный
  ответ ничего не стоит;
- **SNI = хост из `open`** — иначе проверяется одно имя, а TLS идёт к другому виртуальному хосту на
  том же IP. Нет SNI («no sni»), другое имя («sni mismatch»), не TLS вовсе («not tls») — отказ;
- подключение — **к проверенному адресу**, а не к имени ещё раз: второй резолв — это DNS rebinding.

Отказ — это `rst` с причиной, а не тишина: клиент должен уметь отличить «этот мост не обслуживает
твой сервер» от «мост умер».

Две честные оговорки. Кто поднимет свой «хоумсервер», отвечающий на `/versions`, проведёт через мост
любой TLS до себя. Это не дыра, а предел метода: проверки защищают *чужие* сайты от трафика через
мост — спам, скрейпинг, атаки, всё, за что отвечал бы оператор, — а не мешают человеку дойти до
своего сервера. Ради этого мост и есть. Вторая — **domain fronting**: сверка SNI привязывает хост
только на уровне TLS, а заголовок `Host` внутри TLS мост не видит. Matrix-сервер за общим CDN,
который выбирает сайт по `Host`, открывает дорогу к любому сайту на том же CDN, и изнутри TLS этого
не закрыть. Кому это неприемлемо — перечисляет хосты, а не открывает мост `*`.

Открытый мост (`*`) говорит об этом предупреждением в лог при каждом старте — это решение, и
расплачивается за него трафиком и репутацией оператор. Проверка «это Matrix» идёт только после
`open` с доказательством работы, так что выжать её общий бюджет стоит работы на каждую попытку.

## Закрытый бридж

`ALLOWED_PUBKEYS` превращает бридж в приватный: обслуживаются только перечисленные ключи, остальные
не получают даже отказа — просто тишину. Публичный ключ открытого бриджа по природе своей публичен,
так что рассчитывать стоит на то, что им воспользуется кто угодно.

## Проверка

```sh
cargo test --workspace          # сквозные тесты: relay и TLS-хоумсервер поднимаются в процессе
cargo clippy --workspace --all-targets
```

`crates/iskra-bridge/tests/blind.rs` — главное, что тут есть. Он поднимает relay через
`nostr-relay-builder`, хоумсервер с настоящим TLS и сертификатом на `localhost`, берёт настоящего
клиента из `iskra-tunnel-probe` и проверяет, что запрос внутри TLS дошёл, ответ вернулся байт в байт,
отказы приходят словами, а reqwest — тот самый HTTP-клиент из SDK — ходит через CONNECT-прокси со
своим TLS. `tests/blind_logs.rs` пишет все логи процесса на `trace`, проводит через мост токен, пароль
и тело — и не находит в логах ни одного из них. Никакого задеплоенного бриджа и никакой сети.

Против живого моста — тот же клиент одной командой:

```sh
BRIDGE_PUBKEY=<npub из лога бриджа> \
RELAY_LIST=wss://nos.lol,wss://relay.primal.net \
cargo run -p iskra-tunnel-probe -- matrix-client.matrix.org /_matrix/client/versions
```

Если печатается список версий Matrix — туннель работает. `PROBE_REPEAT=20` повторяет запрос по
тому же соединению и печатает min/median/max; `PROBE_PRIVKEY` — ключ, если мост закрыт.

## Устройство

```
crates/
  iskra-tunnel-proto/   формат на проводе: кадр потока, окно, сборка, NIP-44. Без сетевых вызовов.
  iskra-bridge/         config · listener (nostr) · stream (потоки) · blind (куда можно)
                        sni (имя из ClientHello) · ratelimit · upstream (список хостов)
  iskra-tunnel-probe/   клиентская сторона и CONNECT-прокси; ими же пользуются тесты
```

`iskra-tunnel-proto` линкуется **обеими** сторонами туннеля, и это главное решение в раскладке:
отправитель, который режет поток одним способом, и получатель, который собирает его другим, ломались
бы только под нагрузкой, только иногда и только в проде. Здесь один кадр, одно окно и одна сборка, а
их юнит-тесты и есть спецификация — Swift-стороне задают те же вопросы.

### События

| kind | направление | смысл |
|---|---|---|
| 20005 | бридж → клиент | список relay, размер сегмента, сложность PoW — зарезервирован |
| 20010 | клиент → бридж | кадр потока: `open`, `data`, `ack`, `fin`, `rst` |
| 20011 | бридж → клиент | кадр потока: `opened`, `data`, `ack`, `fin`, `rst` |

Всё в диапазоне 20000–29999: это эфемерные события, relay их не хранит, и хранить их незачем — обе
стороны онлайн, а туннель, оставляющий следы на чужом relay, противоречит сам себе.

**В открытых тегах только `#p` с ключом получателя.** Идентификатор потока лежит *внутри*
шифрованного content, а не в теге: тег виден relay и склеил бы кадры одного соединения для любого
наблюдателя. Цена — бриджу приходится расшифровать каждое входящее событие; это дёшево.

### Поток

Клиент шлёт `open` с хостом, портом и первыми байтами соединения — ClientHello едет в том же
событии, так что холодное соединение не стоит лишнего круга через relay, а мосту ClientHello нужен
для проверки SNI до того, как он откроет TCP.

- **`seq` свой у каждого направления, по сегментам.** Сегменты приходят не по порядку и по
  нескольку раз; получатель держит их до первой дыры и отдаёт в сокет только непрерывный префикс.
- **Дыра — это обрыв, а не ожидание.** Relay не хранят эфемерные события, и сегмент, который не
  довёз ни один, не придёт. Дыра дольше 5 секунд — `rst` «gap», и HTTP-клиент сверху повторяет
  запрос на новом соединении. Ретрансмиссии нет, пока замер не покажет, что она нужна.
- **Окно.** Отправитель держит не больше 1 МиБ и 64 сегментов неподтверждённого; получатель
  подтверждает *записанное в сокет* — не полученное — раз в 8 сегментов или 256 КиБ. Упёрся в окно —
  перестал читать свой сокет, и обратное давление доходит до хоумсервера через TCP: ни мост, ни
  телефон не копят в памяти чужую загрузку. Отправитель, который окна не соблюдает, получает `rst`
  «window».
- **Склейка.** Сегмент уходит, когда набралось 24 КиБ или сокет молчит 5 мс: событие на каждое
  чтение было бы сотнями событий на одну комнату и баном от волонтёрского relay. 24 КиБ → base64
  (+⅓) → JSON → base64 шифротекста (+⅓) ≈ 44 КБ событие, в пределах обычных для relay 64 КБ;
  считается это от потолка NIP-44 (65535 байт), а не от круглого числа.
- **Ничего не ждёт `OK` от relay.** Кадр публикуется во все сокеты, и всё; ждут только следующего
  кадра с той стороны. Почему — ниже, в «Что нашли замеры».
- **Потолки, которые не обходятся новым ключом:** потоков на ключ и всего, байт в минуту на ключ и
  всего, события до расшифровки. Закрытый поток помнится 10 минут, чтобы поздняя копия `open` с
  медленного relay не открыла его снова.
- **Доказательство работы на `open`** (NIP-13). Ключ nostr ничего не стоит, поэтому любой потолок
  «на ключ» обходится новым ключом; работа — нет. `open` майнится до `POW_DIFFICULTY` нулевых бит id
  (по умолчанию 16), с тегом `nonce`, в котором записана цель, — мост засчитывает не больше неё,
  чтобы дешёвое событие не прошло случайно удачным id. Телефону это доля секунды раз на соединение,
  рассылке — на каждое. Сегменты внутри потока работы не несут, иначе фото стоило бы сотни
  доказательств. Поток открывает **только** `open`: сегмент, обогнавший свой `open`, теряется, и
  дыра сбрасывает поток — редкость, потому что после ClientHello клиент молчит до ответа сервера.
- **Сложность — в самом отказе.** Мало работы — `rst` `pow 20`: клиент запоминает 20 и майнит
  следующий `open` до неё. Поднять цену при атаке можно без обновления приложения и без отдельного
  события конфига.

## Клиент в приложении

Вторая половина туннеля — в `Core/Sources/IskraCore/Transport/`: `LocalConnectProxy` — слушатель на
`127.0.0.1`, который понимает только `CONNECT` и требует свой секрет в `Proxy-Authorization`, и
`NostrStreamTunnel` — потоки поверх relay. SDK строится с настоящим адресом хоумсервера и
`.proxy(url:)`, так что TLS у него свой, и выше транспорта никто о nostr не знает.

Мост выбирают в приложении: **Настройки → Соединение**. Там два списка. **Публичные мосты** —
проверенные, из репозитория [`iskra-app/public-bridges`](https://github.com/iskra-app/public-bridges)
(формат и что значит «проверенный» — в его README); приложение раз в сутки скачивает список
напрямую с GitHub или с зеркала jsDelivr, а снимок вшит в сборку. **Свои мосты** — сколько угодно,
у каждого название, адрес (`npub1…` или hex — та самая строка, которую мост печатает при старте) и
relay (пусто — три по умолчанию); используется отмеченный. Там же ключ самого устройства (его
вписывают в `ALLOWED_PUBKEYS` закрытому мосту) и кнопка «Проверить мост». С вписанным адресом мост, который не поднялся, — это отказ
(`AuthenticationError.bridgeUnavailable`), а не тихое прямое соединение: переключатель — это решение
о том, кто видит трафик.

Криптография на той стороне — libsecp256k1 (пакет `21-DOT-DEV/swift-secp256k1`) плюс CryptoKit.
ChaCha20 выписан руками ровно потому, что CryptoKit его не отдаёт: у него есть только AEAD
`ChaChaPoly`, а NIP-44 нужен голый поток со своим HMAC. `NIP44Tests` прогоняет через него
официальный вектор-файл NIP.

## Стресс

Тяжёлая нагрузка живёт в `crates/iskra-bridge/tests/stress.rs`, против relay и хоумсервера в том же
процессе. Все тесты помечены `#[ignore]`, поэтому обычный `cargo test` остаётся быстрым:

```sh
cargo test --release --test stress -- --ignored --nocapture
```

Это осознанная граница: тысячи событий в минуту на волонтёрский публичный relay — атака, как её ни
называй.

| Что | Итог (M-ноутбук) |
|---|---|
| 64 потока сразу от одного клиента, по 64–127 КиБ | все целые, p50 130 мс, max 192 мс |
| 32 разных ключа, по 256 КиБ | все обслужены, p50 163 мс |
| 8 МиБ вниз, пять раз подряд | байт в байт, p50 171 мс |

## Целая сессия через мост, и сколько она стоит

`LiveBridgeSessionTests` гоняет настоящий SDK через настоящий мост и три публичных relay по
умолчанию до демо-хоумсервера с TLS, который живёт внутри приложения: вход, sliding sync до полного
списка чатов, открыть комнату, отправить сообщение, дождаться ответа собеседника, подгрузить страницу
истории. Та же сессия идёт ещё раз напрямую, так что разница — цена туннеля и ничего больше.

```sh
(cd Bridge && cargo build -p iskra-bridge)
ISKRA_LIVE_BRIDGE_SESSION=1 swift test --filter LiveBridgeSessionTests
```

Замер 2026-10-17, PoW 16 бит, в скобках — прежний протокол на той же сессии:

| | напрямую | через мост |
|---|---|---|
| вход | 0,29 с | 1,13 с (0,93) |
| список чатов | 0,17 с | 1,08 с (1,0) |
| сообщение ушло | 0,06 с | 0,33 с (0,45) |
| ответ собеседника пришёл | 1,18 с | 1,18 с (1,25) |
| страница истории | 0,10 с | 0,53 с (0,41) |

**SDK держит соединения живыми**: 23 запроса сессии прошли через 6 потоков, так что TLS-рукопожатие
через relay платится раз на соединение, а не на запрос, — это и был вопрос, от которого зависело,
годится ли слепой режим в режим по умолчанию. Годится: он идёт вровень с прежним, а на входе дороже
на холодный TLS и PoW. Одиночный шаг — 200–500 мс, и это цена relay, а не кода.

## Что нашли замеры и стресс

Это было найдено ещё на прошлом протоколе, и каждый пункт держится тестом и сейчас.

**Ничего не должно ждать `OK` от relay.** `send_event` в nostr-sdk возвращается не когда событие
ушло, а когда **каждый** relay пула ответил или истёк таймаут — 10 секунд для лежащего relay. Ответ
из трёх событий, посланных по очереди, ждал мёртвого соседа дважды: список чатов появлялся за 20,8
секунды вместо одной. Одно событие этого не показывало никогда — клиент получает его с живого relay
задолго до того, как мёртвый будет брошен. Теперь всё публикуется сразу и без ожидания;
`a_dead_relay_does_not_hold_up_a_download` гоняет мегабайт с мёртвым relay в списке.

**`while let Ok(..) = notifications.recv().await` — ловушка, и она стоила бы бриджа.** Уведомления
приходят по bounded broadcast-каналу; при переполнении `recv` отдаёт `Lagged`, и очевидная запись
через `while let Ok` **выходит из цикла**. Бридж после одного всплеска трафика замолкал бы навсегда —
оставаясь подключённым, подписанным и здоровым на вид в логах. `Lagged` — это предупреждение и
`continue`, выход только по `Closed`. То же на клиентской стороне.

**Один приёмник уведомлений на всё, а не на каждое соединение.** Иначе каждый видит трафик всех
остальных, работа квадратична, канал переполняется, и пришедшее некому отдать. Одна задача-диспетчер
разбирает поток и раздаёт кадры по id потока. Swift-клиент устроен так же.

**Relay отваливаются, и это нормальный режим работы.** `relay.damus.io` в момент замера отвечал
`503` на само подключение, и ни один запрос при этом не потерялся: событие уходит на все relay, а
дубликаты отбрасываются. Список из одного relay — ошибка, а не упрощение. Что одно событие с трёх
relay — это одно соединение с хоумсервером, держит `a_stream_on_several_relays_reaches_the_homeserver_once`.

**У `RelayBuilder::default()` потолок — 60 событий в минуту.** В тестах он поднят, но само число
стоит помнить: это правдоподобная настройка живого relay, а поток тратит событие на каждые 24 КиБ.
Для медиа это довод за свой relay рядом с мостом, а не за терпение чужого.
